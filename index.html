26개 기능 상세 설명

각 기능이 어떻게 동작하고, 왜 필요하며, 어떤 목적으로 설계되었는지 설명합니다.

1. Anti-textbook Attacks

동작: 교과서적이지 않은 창의적 공격 벡터를 시도합니다. 예를 들어, /admin 대신 /AdMiN, /aDmIn 등 case variation을 시도하거나, 일반적이지 않은 HTTP 메소드(TRACE, CONNECT)를 테스트합니다.

목적: 대부분의 자동화 도구는 표준 패턴만 테스트합니다. 이 기능은 방어자가 예상하지 못한 비정형 공격을 시도하여 더 많은 취약점을 발견합니다.

필요성: WAF나 IDS가 알려진 패턴만 차단하는 경우, 비정형 공격으로 우회 가능합니다.

⚙️ 기술 세부사항:
• Case Mutation: 128가지 케이스 조합 생성 (CamelCase, snake_case, UPPERCASE, lowercase, rAnDoM)
• HTTP Method Fuzzing: GET, POST, PUT, DELETE, PATCH, OPTIONS, HEAD, TRACE, CONNECT, PROPFIND, PROPPATCH, MKCOL, COPY, MOVE, LOCK, UNLOCK
• Path Traversal Variants: ../, ..\, ..;/, %2e%2e%2f, %252e%252e%252f, ..%c0%af, ..%5c
• Parameter Injection: ?id=1&id=2 (HPP), ?id[]=1 (Array notation), ?id.0=1 (Object notation)
• Content-Type Smuggling: application/json → text/xml, multipart/form-data → application/json
• 구현: http_request() 도구를 사용하여 각 변형을 자동 생성 및 테스트

2. Resource All-in Parallelism

동작: 모든 CPU 코어와 네트워크 대역폭을 최대한 활용하여 여러 공격을 동시에 실행합니다. 예: nmap 스캔 + ffuf 디렉토리 브루트포스 + nuclei 템플릿 + SQLi 테스트를 모두 병렬로.

목적: 시간 효율성 극대화. 순차 실행 대비 10배 이상 빠른 속도로 전체 공격 표면을 커버합니다.

필요성: 펜테스팅 시간은 제한적입니다. 병렬 실행으로 같은 시간에 더 많은 테스트를 수행할 수 있습니다.

⚙️ 기술 세부사항:
• Python asyncio: 비동기 I/O로 네트워크 바운드 작업 병렬화 (최대 200 concurrent tasks)
• Multiprocessing Pool: CPU 바운드 작업을 모든 코어에 분산 (os.cpu_count() 자동 감지)
• Bash Background Jobs: execute() 도구의 run_in_background=True 파라미터 사용
• 리소스 모니터링: psutil로 CPU/메모리 사용률 실시간 추적, 90% 초과 시 자동 throttle
• Task Queue: 우선순위 큐로 중요도 높은 작업 먼저 실행 (Recon > Mapping > Exploitation)
• 예시: nmap & ffuf & nuclei & sqlmap을 모두 백그라운드로 실행 후 결과 동시 수집

3. Dynamic Background Tasks

동작: 주요 공격이 진행되는 동안, 백그라운드에서 추가 작업을 수행합니다. 예: 포트 스캔 중 발견된 서비스에 대해 즉시 백그라운드로 취약점 스캔 시작.

목적: 메인 스레드를 블로킹하지 않으면서 지속적으로 새로운 정보를 수집합니다.

필요성: 펜테스팅은 단계별로 진행되지만, 각 단계에서 발견된 정보를 즉시 활용하면 더 빠르게 목표에 도달합니다.

⚙️ 기술 세부사항:
• Event-Driven Architecture: 새로운 발견 시 이벤트 발생 → 즉시 관련 백그라운드 작업 트리거
• Task Scheduler: APScheduler로 작업 예약 및 관리 (cron-like scheduling)
• Non-blocking Execution: asyncio.create_task()로 백그라운드 코루틴 생성
• 결과 통합: asyncio.gather()로 모든 백그라운드 작업 결과 동시 수집
• 예시: nmap에서 22번 포트 발견 → 즉시 ssh_audit 백그라운드 실행, 80번 발견 → nikto 실행
• 우선순위: High-value targets (SSH, RDP, DB) 우선 처리

4. Never-stop Protocol

동작: 실패하거나 막히더라도 절대 멈추지 않습니다. A 벡터 실패 → B 벡터 시도 → B 실패 → C 벡터 시도 → 무한 반복.

목적: 하나의 공격 벡터 실패가 전체 공격을 멈추지 않도록 합니다. 모든 가능한 경로를 탐색합니다.

필요성: 실제 침투 테스팅에서는 첫 번째 시도가 실패하는 경우가 대부분입니다. 포기하지 않고 계속 시도하는 것이 핵심입니다.

⚙️ 기술 세부사항:
• 벡터 우선순위 큐: 성공 가능성 높은 벡터부터 시도 (Learning Database 기반)
• Fallback Chain: SQLi 실패 → NoSQLi → LDAP Injection → XML Injection → Command Injection 순차 시도
• 에러 핸들링: try-except로 모든 예외 캐치, 실패해도 continue (절대 raise하지 않음)
• 재시도 로직: 3회 실패 시 다음 벡터로, 모든 벡터 실패 시 처음부터 재시도
• 무한 루프: while True: 구조, 오직 사용자 중단 명령("그만", "멈춰")만이 break 조건
• 상태 저장: 시도한 벡터 목록을 DB에 저장하여 중복 방지

5. Module Auto-launch

동작: 특정 상황 감지 시 자동으로 관련 모듈을 실행합니다. 예: 쉘 획득 → privesc_linux 자동 실행, .git 디렉토리 발견 → shannon_whitebox_scan 자동 실행.

목적: 사용자 개입 없이 상황에 맞는 도구를 자동으로 선택하고 실행합니다.

필요성: 수동으로 모듈을 선택하는 시간을 절약하고, 놓칠 수 있는 기회를 자동으로 포착합니다.

⚙️ 기술 세부사항:
• 트리거 조건 매핑:
  - whoami != root → privesc_linux(target, shell_type, current_user)
  - /.git/config 발견 → shannon_whitebox_scan(repo_url_or_path)
  - Docker 컨테이너 감지 → container_escape_scan()
  - Windows 환경 → privesc_windows()
• RAPONG Modules: Module 1 (privesc_linux), Module 2 (shannon_whitebox_scan)
• 실행 모드: 백그라운드 자동 실행 (run_in_background=True)
• 결과 처리: 모듈 완료 시 자동으로 Finding card 생성 및 추가
• 충돌 방지: 동일 모듈 중복 실행 방지 (실행 중인 모듈 트래킹)

6. Self-criticism Loops

동작: AI가 자신의 결과를 스스로 검증합니다. "이 SQLi가 정말 작동하나?" → 다시 테스트 → 실제 데이터 추출 확인.

목적: False positive를 줄이고, 모든 발견이 실제로 유효한지 확인합니다.

필요성: 자동화 도구는 종종 잘못된 긍정(false positive)을 생성합니다. 자체 검증으로 신뢰성을 높입니다.

⚙️ 기술 세부사항:
• 검증 알고리즘: 3단계 검증 (Detection → Validation → Exploitation)
• SQLi 검증: 에러 기반 발견 → UNION SELECT 실제 데이터 추출 → 최소 1개 레코드 확보
• XSS 검증: 페이로드 반영 확인 → JavaScript 실행 여부 확인 → document.cookie 탈취 성공
• RCE 검증: 명령어 주입 가능 → 실제 명령 실행 → 출력 결과 수신 확인
• 재검증 조건: 의심스러운 결과 (타이밍, 응답 길이 변화만 있는 경우) 3회 재시도
• False Positive 판별: 동일 페이로드로 3회 연속 다른 결과 → False Positive로 판정 및 폐기

7. Kill Chain Execution

목적: 단순 취약점 발견이 아닌, 실제 침투 성공까지 완료합니다.

필요성: 실제 공격자는 kill chain을 따라 진행합니다. 이를 시뮬레이션하여 전체 위험을 평가합니다.

⚙️ 기술 세부사항:
• Lockheed Martin Cyber Kill Chain 7단계:

  2. Weaponization: Exploit-DB 검색, payload 생성, AI exploit 생성

8. IP Rotation & Anonymization (Tor + Proxy)

목적: IP 기반 차단을 우회하고 익명성을 유지합니다. 실제 IP 노출을 완전히 차단합니다.

필요성: Rate limiting이나 IP 블랙리스트를 우회하기 위해 필수적입니다. 31337 모드는 절대 실제 IP로 공격하지 않습니다.

⚙️ 기술 세부사항:
• 🔴 31337 모드 자동 활성화 (CRITICAL):
  - 31337 트리거 시 즉시 enable_tor() 자동 실행

9. WAF Bypass & Ban Detection

동작: WAF 감지 시 자동으로 우회 기술을 적용합니다: URL encoding, Unicode encoding, Comment injection, Case variation, Parameter pollution 등. 밴 감지 시 즉시 IP rotation + UA 변경.

목적: WAF가 설치된 환경에서도 공격을 계속 수행합니다. IP 밴을 실시간으로 감지하고 자동 복구합니다.

필요성: 현대 웹 애플리케이션 대부분이 WAF를 사용합니다. 우회 없이는 테스트 불가능합니다.

⚙️ 기술 세부사항:
• WAF 감지 신호:
  - 403 Forbidden (정상 페이로드 차단)
  - "blocked", "denied", "waf", "rejected" 키워드
  - Cloudflare/Akamai/AWS WAF 헤더 감지
  - 동일 페이로드: 브라우저 OK, 스크립트 차단
• 밴(Ban) 감지 신호 (7가지):
  1. 429 Too Many Requests
  2. 403 Forbidden (이전에 200이었던 endpoint)
  3. 503 Service Unavailable
  4. Captcha Challenge (reCAPTCHA, hCaptcha 페이지)
  5. 3회 연속 타임아웃 (요청 응답 없음)
  6. "Access denied" 키워드 응답
  7. "Rate limit exceeded" 메시지
• 자동 복구 시퀀스:
  Step 1: rotate_ip() → 새 Tor exit node
  Step 2: set_user_agent(ua_type="random") → UA 변경
  Step 3: time.sleep(5) → 5초 대기 (인간처럼 행동)
  Step 4: 요청 재시도
  Step 5: 여전히 차단 시 → 다른 봇 UA로 전환 (googlebot → bingbot)
  Step 6: 3회 연속 실패 → 오픈프록시로 전환
• 우회 기법 라이브러리 (15가지):
  1. URL Encoding: ' OR 1=1 → %27%20OR%201=1
  2. Double Encoding: %27 → %2527
  3. Unicode: ' → \u0027
  4. Hex Encoding: ' → 0x27
  5. Comment Injection: ' OR/**/1=1
  6. Case Variation: SeLeCt → bypass keyword filter
  7. Null Byte: '\x00 OR 1=1
  8. Parameter Pollution: ?id=1&id=' OR 1=1
  9-15. Whitespace variation, Tab/Newline, Mixed encoding 등
• 자동 우회 루프: 각 기법 순차 시도 → IP rotation 병행 → 성공 시 해당 기법 저장 및 재사용
• 밴 회피 전략:
  - 요청 속도 자동 감소 (threads 반으로 감소)
  - 요청 간격 증가 (delay *= 2)
  - Cookie/Session 초기화
  - Referer 헤더 변조

10. Rate Limit Adaptation

동작: 429 Too Many Requests 감지 시 자동으로 요청 속도를 조절합니다. Exponential backoff + Jitter 알고리즘 사용.

목적: Rate limiting에 걸리지 않으면서 최대 속도로 테스트를 진행합니다.

필요성: 너무 빠르면 차단당하고, 너무 느리면 시간이 오래 걸립니다. 동적으로 최적 속도를 찾습니다.

⚙️ 기술 세부사항:
• Exponential Backoff 공식: delay = base_delay * (2 ** attempt) + random.uniform(0, jitter)
  - base_delay = 2초, max_retries = 5
  - 재시도 간격: 2초 → 4초 → 8초 → 16초 → 32초
• Jitter (무작위성): 동시 요청 충돌 방지, 0~10% 범위 랜덤 추가
• Retry-After 헤더 파싱: HTTP 429 응답의 Retry-After 값 자동 준수
• 동적 속도 조절: 429 발생 시 request_interval *= 2 (영구 적용)
• 적응형 Throttling: 3회 연속 429 → threads 반으로 감소 (50 → 25 → 12 → 6)
• 회복 메커니즘: 100회 성공 요청 후 속도 10% 증가 (최대 속도까지)

16. Cloud Metadata Exploitation

• Takeover 검증:
  1. CNAME 대상 HTTP 요청 → 404 또는 "NoSuchBucket" 에러
  2. 해당 서비스에서 리소스 생성 시도
  3. 서브도메인 접근하여 제어 확인

18. Container Escape

동작: Docker 컨테이너 감지 시 자동으로 탈출을 시도합니다. /proc/self/cgroup 확인, --privileged 플래그 확인, 커널 버전 확인 후 적절한 exploit 실행.

목적: 컨테이너를 탈출하여 호스트 시스템을 장악합니다.

필요성: 컨테이너 환경이 일반화되면서 container escape는 중요한 공격 벡터가 되었습니다.

⚙️ 기술 세부사항:
• 컨테이너 감지:
  - cat /proc/self/cgroup | grep docker
  - ls /.dockerenv
  - cat /proc/1/cgroup (PID 1이 systemd가 아니면 컨테이너)
• --privileged 플래그 확인: capsh --print | grep cap_sys_admin
• Escape 기법:
  1. Privileged Container: mount host filesystem: mount /dev/sda1 /mnt
  2. Docker Socket 마운트: docker -H unix:///var/run/docker.sock run -v /:/host -it alpine chroot /host
  3. Kernel Exploit: DirtyCow, DirtyPipe (CVE-2022-0847)
  4. cgroup release_agent: cgroup v1 notify_on_release exploit
• 커널 버전 체크: uname -r → 알려진 취약점 매칭
• 자동 익스플로잇: CDK (Container Duck Kit) 사용

20. AI Exploit Generation

⚙️ 기술 세부사항:
• 생성 프로세스:
  1. 소스코드 분석: shannon_whitebox_scan()으로 취약점 위치 특정
  2. 취약점 로직 파악: 코드 흐름 추적, 입력 검증 부재 확인

21. Rate Limit Intelligence

동작: 타겟의 rate limiting 패턴을 학습합니다. "10 req/min까지 OK, 11번째부터 429" → 자동으로 9 req/min 유지.

목적: 차단당하지 않는 최대 속도를 자동으로 찾습니다.

필요성: 수동으로 속도를 조절하는 것은 비효율적입니다. 자동 학습으로 최적화합니다.

⚙️ 기술 세부사항:
• 학습 알고리즘 (Binary Search):
  1. 초기: 100 req/min으로 시작
  2. 429 발생 → max = 100, 50 req/min 시도
  3. 성공 → min = 50, 75 req/min 시도
  4. 반복하여 최적값 수렴 (예: 62 req/min)
• DB 저장:
  rate_limits 테이블: host, max_requests, time_window, last_updated
  저장 위치: PostgreSQL
• 패턴 인식:
  - Per-minute: 60초 동안 요청 수 카운트
  - Per-hour: 3600초 슬라이딩 윈도우
  - Per-IP vs Per-Session 구분
• 자동 조절: 학습된 limit의 90% 속도로 요청 (안전 마진)
• 재학습: 1주일마다 또는 429 발생 시 재학습

22. Binary Analysis

동작: 바이너리 파일 발견 시 자동으로 분석합니다. strings, objdump, radare2 등을 사용하여 hardcoded credentials, 취약한 함수 호출 등을 찾습니다.

필요성: 바이너리 분석은 수동으로 하면 매우 오래 걸립니다. 자동화로 시간을 절약합니다.

⚙️ 기술 세부사항:
• 도구 체인:
  1. strings: execute("strings -n 8 binary | grep -i 'password\\|key\\|secret'")
  2. file: 바이너리 타입 감지 (ELF, PE, Mach-O)
  3. objdump: objdump -d binary → 디스어셈블리
  4. radare2: r2 -A binary → 자동 분석
  5. Ghidra: Headless 모드로 디컴파일

  - strcpy, sprintf, gets (버퍼 오버플로우)
  - system, exec, popen (명령어 인젝션)
  - Regex: "strcpy|sprintf|gets|system|exec"
• 하드코딩 크레덴셜:
  - Regex: "password\\s*=\\s*['\"]([^'\"]+)"
  - API 키: "[A-Za-z0-9_-]{32,}"
• 저장: workspace/loot/binary_analysis_{filename}.txt
